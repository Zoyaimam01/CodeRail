## 1. Core Mental Models

Greedy algorithms are all about making the **locally optimal choice** at each step with the hope of eventually reaching the **globally optimal solution**. It’s like climbing a mountain where you always choose the steepest path upward, trusting that it will eventually lead you to the summit. 

The fundamental observation you need to make is **monotonicity** or **matroid properties** (fancy words for: *does taking this choice now ever hurt my future options?*). When a problem fits a greedy pattern, you'll notice that ordering the data in a specific way (by starting time, cost, size, or value) allows you to make irrevocable decisions. Once you make a choice, you never have to look back or undo it. If you find yourself wondering "what if I made a different choice earlier?", it's usually a sign that greedy doesn't work, and you might need dynamic programming or backtracking instead.

## 3. Reusable Code Patterns

When tackling greedy problems, I almost always start by sorting my data. Here is the mental template I keep in my head—usually involving a custom sort followed by a single pass:

```cpp
void solve() {
    int n;
    cin >> n;
    vector<pair<int, int>> items(n);
    for (int i = 0; i < n; i++) {
        cin >> items[i].first >> items[i].second;
    }

    // Step 1: Sort by our chosen greedy criteria (e.g., ending time or cost)
    sort(items.begin(), items.end());

    int ans = 0;
    int last_action_point = -1;

    // Step 2: Make the greedy sweep
    for (int i = 0; i < n; i++) {
        if (items[i].first >= last_action_point) {
            ans++;
            last_action_point = items[i].second; // Lock in the local optimum
        }
    }

    cout << ans << "\n";
}
```

## 4. Traps & Common Gotchas

*   **Sorting the wrong key:** The biggest trap in greedy is sorting by $A$ when you actually needed to sort by $B$ (or a combination of both). Always test your sorting logic with a quick manual dry-run on a tiny example.
*   **Floating-point precision issues:** If your greedy choice involves ratios or division (like fractional knapsack or slope comparisons), avoid `double` or `float`. Stick to cross-multiplication (`a * d > b * c`) to maintain exact integer precision.
*   **Greedy vs. Brute Force overlap:** Sometimes a problem *looks* greedy, but a local choice ruins a global constraint. If a problem has tight constraints ($N \le 20$), it's almost never pure greedy—think recursion or bitmasking instead. 
*   **Off-by-one boundary conditions:** When making interval-based greedy choices, be paranoid about strict inequalities (`>` vs `>=`). Missing an equality check can cause you to skip valid overlapping elements.
